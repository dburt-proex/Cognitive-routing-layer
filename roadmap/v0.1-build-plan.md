## What v0.1 deliberately does not do

Each of these is a decision, not an oversight:

| Not built | Why |
|---|---|
| Model adapter for operator generation | The fixture adapter makes runs byte-reproducible, which is what let the contract layer be tested at all. Adding generation before the contracts were proven would have made failures ambiguous |
| Authentic CASA verifier | Requires CASA's real issuance mechanism. The interface and all seven binding checks exist; the default fails closed |
| Durable persistence | Mirdexx and the Shared Decision Ledger own this. Building it here would create a competing system of record |
| Visual interface | Specified in `docs/product-interface.md`. The core stays independent of it |
| Confidence calibration | Requires outcome data from real decisions. Until then the values are labelled uncalibrated |
| The four deferred operators | Each has a specific technical prerequisite in `spec/operators.yaml`, not a vague "later" |

## v0.1.1 — hardening

Small, self-contained, no schema breaks.

| Item | Rationale |
|---|---|
| Semantic contradiction detection as a second pass | Structural detection misses disagreement expressed in different vocabulary about differently-labelled subjects. A second pass would report separately so the structural guarantee stays intact |
| Operator timeout enforcement | The policy declares `operator_timeout_seconds` and the failure path. The synchronous fixture adapter cannot time out, so the path is unexercised until the model adapter lands |
| Evidence staleness | `expires_at` exists on the evidence record and nothing reads it. Stale evidence should reduce the ceiling the way the Leverage Engine invalidates stale repository snapshots |
| Receipt diff | Compare two runs of the same problem: assumptions surfaced, evidence introduced, options rejected, confidence moved. Needed for the flagship demonstration's strongest panel |
| Superseding-run linkage | The correction model is documented; `supersedes_run_id` is not yet a receipt field |

## v0.2 — generation and integration

The order matters. Each item depends on the one above it.

### 1. Model adapter

Replace the fixture adapter with a model-backed one behind the same interface.

The router does not change. Classification, route selection, convergence, and
the audit stay deterministic; only operator payload content becomes generated.
Contract enforcement is what makes this safe: a generated payload passes
through exactly the same required-transformation checks, and a model that
produces three restatements of one option fails `DV-F2` the same way a fixture
does.

Prerequisite: PromptBP owns the instruction layer that produces payloads
conforming to `operator-output.schema.json`. That boundary is already
documented.

Acceptance: every existing fixture reproduces its expected receipt shape with
generated content, and the adversarial contract tests still fire.

### 2. Authentic CASA verification

Implement `CasaVerifier` against CASA's issuance mechanism. The interface and
binding checks are done; what is missing is trust establishment — issuer
identity, key distribution, signature scheme.

Until it exists, no production configuration may use `TestAdapterVerifier`, and
no material may describe CASA integration as working.

### 3. Leverage Engine consumption

The first real consumer. A directive carries an RCP receipt so the ranking can
cite reasoning coverage rather than assert it.

This is also the test of whether the receipt schema is right. A schema that has
never survived a consumer is a guess, and this is where the guess gets
corrected — which is precisely why the "versioned package" placement option was
deferred rather than taken now.

### 4. Deferred operators, one at a time

| Operator | Prerequisite |
|---|---|
| **Janusian** | A contradiction taxonomy separating productive tension from unresolved conflict. Today the gate flags exactly what this operator produces |
| **Analogical** | A structural-mapping validity check, so it does not degrade into surface similarity |
| **Lateral** | A re-entrant router able to restart classification, since its value is reframing the problem the run was classified on |
| **Associative** | A scoring method for connection quality. Unscoreable output cannot enter evidence-weighted convergence |

Each ships with contract, transformations, failure conditions, fixtures, and
adversarial tests before it is admitted to the locked set.

### 5. Calibration study

Once enough receipts exist with known outcomes, relate confidence to
correctness. Until that runs, the `uncalibrated_decision_support_score` label
stays on every value in every receipt.

## Sequencing rule

Do not start v0.2 until the validation protocol in
`commercialization/offer-ladder.md` has run against six real decisions with a
control group. It has a written falsification condition: if the rework
decisions produce no non-obvious material findings while the successful
decisions produce false criticals at a similar rate, the load-bearing
commercial assumption is wrong.

That result would mean stopping, not building v0.2 anyway. Building generation
and integration before knowing whether anyone values the output is how a
technically sound system becomes an expensive one.

## New engineer, first hour

```bash
git clone <repo> && cd Cognitive-routing-layer
PYTHONPATH=src python -m unittest discover -s tests -v
PYTHONPATH=src python -m cognitive_routing_layer.cli --run confidence-does-not-authorize
```

Then read, in order: `docs/architecture.md` for the pipeline and the placement
decision, `spec/operator-contract.md` for what an operator actually is, and
`spec/operators.yaml` for the nine contracts. `docs/integration-boundaries.md`
covers what this system must not do on another system's behalf.

The single most useful thing to understand first: the router is deterministic
and only operator content is generated. Every design choice follows from that.
